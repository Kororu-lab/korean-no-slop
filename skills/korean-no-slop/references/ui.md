# UI와 웹페이지

화면에서 사용자가 읽고 결정하고 조작하는 데 필요한 문구를 남긴다.

## 새 화면

화면 제목, 현재 상태, 입력 레이블, 선택지, 행동을 먼저 정한다. 부제·설명·도움말은 제목만으로 알 수 없는 정보가 있을 때 추가한다. 프레임워크나 디자인 시스템에 설명 슬롯이 있어도 내용의 필요성을 먼저 판단한다.

| 위치 | 기본 형식 | 설명이 필요한 경우 |
| --- | --- | --- |
| 메뉴·탭 | 대상이나 기능 이름 | 이름만으로 기능을 구분하기 어려운 경우 |
| 버튼 | 실행할 행동 | 실행 결과에 중요한 비용·손실·조건이 있는 경우 |
| 화면·카드 제목 | 구분에 필요한 이름 | 제목과 별개인 범위·기간·조건이 있는 경우 |
| 입력 도움말 | 필요한 형식·제약 | 입력 오류 예방에 필요한 경우 |
| 빈 상태·오류 | 현재 상황과 가능한 행동 | 원인이나 복구 방법을 알려야 하는 경우 |

## 기존 화면

제목 아래 문장을 지워본 뒤, 사용자가 잃는 정보가 있는지 확인한다. 정보가 없으면 요소와 그 요소만을 위한 여백을 제거한다. 내용이 있는 주변 요소의 배치를 살핀다. 모든 카드를 같은 높이로 맞추기 위해 문장을 만들어 넣지 않는다.

컴포넌트의 description prop은 optional로 다룰 수 있는지 확인한다. 필수 스키마라면 기존 계약을 유지하면서 허용된 빈 값·조건부 렌더링을 사용한다. 문구를 생략했다는 이유로 계약이나 기능을 임의 변경하지 않는다.

`aria-describedby` 등이 제거한 요소를 참조하면 관계를 함께 정리한다. 그 문구에 접근성상 필요한 설명이 있으면 정보가 유지되는 방법을 선택한다. 사용자에게 보여줄 필요가 없는 구현 사유나 수정 이력을 화면에 쓰지 않는다.

## 예시

예시는 이 저장소에서 작성한 가상 사례다.

- 제목 `알림 설정`과 설명 `알림 설정을 관리하고 원하는 방식으로 조정하세요.`가 있으면 설명을 제거한다.
- `월간 실적` 아래 `2026년 8월 · 환불 제외`는 기간과 집계 범위를 전달하므로 남긴다.
- `이메일` 아래 `업무용 이메일을 입력하세요.`가 실제 입력 조건이면 남긴다.
- 비교표 제거 요청을 받으면 비교표를 없앤다. 빈자리에는 `공정성을 위해 비교 정보를 제공하지 않습니다.` 같은 문구를 만들지 않는다.

최종 화면에서 중복 문구, 빈 설명 상자의 여백, 깨진 접근성 참조, 잘린 레이블을 확인한다.
